# 开发操作规范

## 使用要求

每次修改程序前，先阅读本文件，确认当前改动没有破坏这里定义的边界。涉及联机比赛、计时、进球、结算、数据库记录时，必须优先遵守本文件。

## 联机比赛职责边界

前端只负责：

- 渲染页面和比赛场景。
- 采集玩家输入。
- 播放本地动作、进球特效、比赛结束特效。
- 向后端查询权威状态和结算数据。

后端负责：

- 匹配。
- 权威比赛状态。
- 回合许可。
- 球员物理上限计算。
- 操作合法性校验。
- 进球判定。
- 比分。
- 胜负。
- 比赛记录、操作记录、进球记录、结算数据入库。

前端可以根据本地物理模型提前播放特效，但不能修改后端比分、进球记录、比赛结果、比赛记录。任何核心结果只能由后端写入数据库，前端只能查询。

## Clock 接口规范

`clock` 只能用于时间轮询。

`clock` 允许做的事情：

- 校验请求用户属于当前比赛。
- 返回服务端当前时间。
- 返回比赛剩余时间。
- 返回当前回合剩余时间。
- 返回计时是否处于暂停状态以及暂停原因。

`clock` 禁止做的事情：

- 禁止推进物理模拟。
- 禁止写数据库。
- 禁止判断进球。
- 禁止判断胜负。
- 禁止返回场上快照。
- 禁止返回比分。
- 禁止返回 winner/loser。
- 禁止返回球员物理上限。
- 禁止决定或发放操作权限。

比赛场面、比分、进球和结束状态不允许塞回 `clock`。除 `clock` 时间轮询外，联机比赛流程必须采用事件触发请求。

## 联机事件触发规范

联机比赛禁止用高频 `state` 轮询推动比赛。正常比赛流程只允许这些事件点触发请求：

- 场景加载完成后调用 `ready`。
- 收到 `ready.started=true` 后调用 `turn-request`。
- `turn-request` 返回“不是你的回合”后，前端可以每 250ms 调用 `opponent-action` 查询对手操作；收到一条对手操作、获得本方操作权、断开连接或比赛结束时必须停止该轮询。
- 本地播放完一次自己或对手的操作，所有球和球员完全静止后调用 `turn-request`。
- 进球特效播放结束后调用 `score` 查询权威比分，再按场上静止事件调用 `turn-request` 查询回合许可。
- `clock` 显示常规时间归零后调用 `finish-check` 查询后端是否已经结束比赛。
- 玩家释放球员后调用 `shoot`。

后端必须独立推进权威实时物理进程，不能依赖前端轮询 `state` 来让比赛继续。前端不上传快照，不用快照校验比赛结果。

## 接口职责规范

接口只负责单独一项职责，或者几个触发条件完全一致、业务边界相同的字段。触发条件不同的功能必须拆成不同接口。

联机比赛接口职责：

- `turn-request` 只负责查询和返回操作许可、球员物理上限、技能触发预留字段。
- `opponent-action` 只负责在非本方回合查询并返回对手已经提交的操作；对手尚未操作时只返回等待，不返回比分、结算或物理上限。
- `score` 只负责在进球事件后查询后端权威比分。
- `finish-check` 只负责在比分到 3 或 clock 归零后查询后端是否准许结束，并在准许结束时返回结算数据。
- `shoot` 只负责提交玩家操作和返回操作是否被后端接收。
- `clock` 只负责时间。

不要把比分、胜负、结算数据塞进 `turn-request`、`shoot` 或 `clock`。

## 轮询使用规范

不要随意使用轮询。新增任何轮询前必须得到明确授权，并在文档中写清楚轮询频率、停止条件、请求字段和为什么不能使用事件触发。

## 操作记录规范

`match_action` 只记录：

- `start`
- `action`
- `end`

进球不写入 `match_action`，统一写入 `match_goal_record`。

## 能力值和技能规范

前端不直接根据球员能力值计算比赛物理上限。后端负责把球员能力、技能触发、临时效果转换成实际物理上限。

前端每次获得操作许可前，必须通过后端返回的本回合物理上限来显示力度圈、方向线和弧线范围。

## 后端地址配置规范

客户端访问后端的开发 IP 统一写在：

`client/assets/scripts/services/BackendConfig.ts`

以后更换电脑 IP 或端口，只改这个文件，不要在业务接口里硬编码 IP。
